# LMS/Blackboard preparation checklist

Use this checklist to turn public repository materials into a local course shell. It is platform-neutral; Blackboard terminology is included because the originating course uses Blackboard. This repository does not supply a Blackboard export, answer keys, active quiz items, grades, or student records.

## 1. Build the learner-facing structure

- Create one LMS unit per course week or module.
- Add the module README as the conceptual/lecture reading and link its tutorial separately.
- Mark the **current assignment** clearly; do not direct students to submit a completed tutorial as their assignment.
- Add the applicable data card, reproducibility checklist, and AI-use boundary.
- Provide accessible document formats, captions/alt text where applicable, and an equivalent route for approved accommodations.

## 2. Configure each assessment

For every quiz, homework, studio, or project, state:

| Required field | Example |
| --- | --- |
| Learning outcome | Diagnose leakage in a time-series split. |
| Assessment mode | AI-free, AI-assisted, or AI-audited. |
| Allowed tools/data | Local Python; no restricted data uploaded to third-party AI. |
| Deliverables | Split plan, baseline, code/notebook, evidence table/figure, limitation audit, AI-use record. |
| Individual evidence | Five-minute defense, live modification, or released-after-submission test condition. |
| Grading criteria | Link or adapt the shared rubric. |
| Due dates/accessibility | Local course policy and approved accommodations. |

Keep numerical quiz variants, answer options, keys, release conditions, and scoring notes in the private instructor area.

## 3. Suggested Blackboard workflow

1. Create an **Orientation** area: course policy, supported software, AI modes, first diagnostic, and data/privacy boundary.
2. Create a **Module** folder: lecture reading, short demo/tutorial, data card, assignment, submission link, and discussion/FAQ.
3. Create a **Supervised checks** area: availability window, allowed materials, LockDown Browser or other local controls if selected, and accessibility alternative.
4. Create a **Project** area: proposal/evidence-plan template, milestones, presentation requirements, and individual-defense scheduling.
5. Create a private **Instructor** area outside learner visibility: keys, item bank, grading notes, late-release tests, and student records.

## 4. Pre-release check

Before making a module visible, confirm:

- every internal/external link and tutorial command works in the intended student environment;
- students have a supported fallback if compute, license, or accessibility conditions differ;
- dataset license, release status, units, and redistribution boundary are explicit;
- assignment language matches the stated AI mode;
- the rubric and individual-evidence mechanism are ready; and
- no keys, restricted data, credentials, or student information are visible to students or committed publicly.

## 5. After grading

Record common errors, broken links, environment failures, accessibility issues, and the effectiveness of the individual check. Update public documentation only with rights-cleared, non-identifying improvements; retain grading records according to institutional policy.
